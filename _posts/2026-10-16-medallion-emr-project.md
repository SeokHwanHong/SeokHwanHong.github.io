[프로젝트 저장소](https://github.com/SeokHwanHong/Medallion) · [분석·보고서 기준 커밋](https://github.com/SeokHwanHong/Medallion/tree/944986c7f124eca2774af2093bc45cd2962dda4d)

**Medallion**은 실습용 합성 외래 EMR을 정제·통합하고, 기준정보·접수·진료·수납의 네 관점으로 운영 개선 방향을 제안한 **1석 3조의 4인 팀 프로젝트**다. 나는 진료·처방 상세·수가 카탈로그 정제, 현장접수 분석·시각화와 노션·GitHub 문서 정리에 참여했다.

핵심은 복잡한 데이터를 하나로 합치는 것에서 끝나지 않았다. **어떤 기록을 분석에 사용할 수 있는지 검증하고, 어느 구간을 먼저 점검할지 근거로 좁히는 것**이 과제였다. 운영 시스템을 실제 병원에 배포하거나 개선 효과를 실증한 프로젝트는 아니다.

## 1. 문제: 외래 과정은 연결돼 있지만 기록은 나뉘어 있다

환자는 예약하거나 현장에 도착하고, 접수 결과에 따라 진료를 받은 뒤 서비스와 수납 기록을 남긴다. 이 과정의 상태·시간·금액이 서로 맞아야 분석이 가능하다. 잘못된 연결이나 일대다 조인에 따른 금액 증폭이 있으면 운영 문제처럼 보이는 현상이 데이터 오류일 수 있다.

팀은 ‘데이터 기반 의료 자원 불균형 해소 및 외래 프로세스 개선’을 대주제로 정하고 네 관점을 연결했다.

| 팀의 분석 관점 | 질문 | 산출물과 해석 범위 |
| --- | --- | --- |
| 기준정보·원천 통합 | A/B 원천의 품질과 환자 연결은 어떤가? | 코드·환자 기준정보 통합 권고 |
| **현장접수 — 내 담당** | 어느 진료과·도착 시간대를 먼저 점검할까? | 반복 고율 구간의 정책·사전 안내 점검 제안 |
| 의사 배치 | 병원·진료과별 부하에 어떤 차이가 있나? | 인력 재배치 시뮬레이션, 실제 효과와 구분 |
| 수납 | 청구·결제·환불이 일치하고 어떤 확인 부담이 있나? | 진료별 대사와 업무 복잡도 시나리오 |

개별 결과를 더해 전체 효율 향상률을 만들지 않았다. 각 분석의 모집단과 측정 단위가 다르기 때문이다.

## 2. 데이터와 처리 구조

분석 대상은 **2023년 1월~2025년 12월의 합성 외래 EMR**이다. 발표 개요에는 약 1,157만 건, 17개 테이블·119개 컬럼, 병원 490개와 의사 4,748명이 제시돼 있다. 실제 정제·분석에서는 재전송 포함 여부와 유효 기준에 따라 건수가 달라진다.

| 처리 단계 | 역할 | 남기는 근거 |
| --- | --- | --- |
| 원천 보존·프로파일링 | 원본 CSV와 테이블별 오류 양상 확인 | 원천 파일·행 위치, 결측·중복·코드 진단 |
| 표준화·정제 | 명세·ERD와 업무 규칙 적용 | 변경 전후 값과 복구 근거 |
| 정상·격리·제외 분리 | 불확실한 값을 억지로 정상화하지 않음 | 사유 태그와 건수 대사 |
| MySQL 적재·연결 검증 | 참조 관계와 시간·금액 확인 | 검증 SQL·보고서 |
| 주제별 추출·분석 | SQL 집계와 Python 재검증 | 분석 단위·기간·분모·입력 해시 |
| 전달 | 차트·보고서·발표자료로 판단 근거 설명 | 관측 결과·제안·한계 분리 |

Polars는 대용량 CSV의 스캔·변환·조인, pandas·NumPy는 분석과 검증, MySQL은 정제 데이터 조회와 주제별 추출에 사용했다. 원천·정제·분석 단계의 구분은 저장소의 메달리온 설계지만, 각 노트북과 DB 작업이 하나의 자동 운영 스케줄러로 완성됐다는 뜻은 아니다.

### 수치가 다른 자료를 어떻게 다뤘는가

저장소에는 1차 정제, 연쇄 격리 이후, DB 추출 시점의 자료가 함께 있다. 예를 들어 develop README의 전체 클린 합계는 7,121,184행이지만 Database 안내에는 7,122,184행으로 기재돼 있다. 현장접수 문서는 정제 데이터 추출로 설명하는 반면 develop README는 감사·격리 로그 포함 모집단으로도 설명한다.

이 글에서는 이 수치를 임의로 통일하지 않는다. **개인 분석의 직접 근거는 01~03 CSV를 대조한 보고서의 298,257건**으로 고정한다. 전체 DB 최종 합계와 이 표본의 정확한 추출 시점·격리 포함 여부는 동일 실행의 manifest·SQL 결과로 다시 고정할 과제로 남긴다. 외래 진료 수와 현장접수 수 역시 다른 사건 단위다.

## 3. 내 역할: 진료·서비스·수가의 근거를 대조하며 정제하기

노션 작업 일지에는 `encounters`, `encounter_services`, `service_catalog`와 공통 코드 사전 점검을 담당한 기록이 있다. 저장소에는 내 이름의 세 정제 노트북이 남아 있다. 노트북의 저장 셀은 정제 CSV·검토 자료·변경 이력·manifest를 만들며 DB 적재는 별도 작업이었다. 서두의 ‘파일 저장 대기’ 문구보다 실제 저장 셀을 기준으로 구현 범위를 확인했다.

| 담당 테이블 | 직접 적용한 판단 | 결과·검토 자료 |
| --- | --- | --- |
| encounters | SEEN 접수와 진료의 연결, 도착→접수→진료 시간 순서, 독립된 서비스·결제 집계 대조 | 정상·검토 분리, 복구 근거와 미완료 교차검증 사유 |
| encounter_services | PK·진료별 순번 충돌, 수량×단가=줄 금액, 진료일의 가격 버전 유효성 | 정상 상세와 검토 상세, 진료 전체 대사 미완료 표시 |
| service_catalog | 연도별 가격 버전, 같은 코드의 기간 중첩, 명칭·단가의 독립 근거 | 복구·경고·격리 이력과 버전별 검증 |

### 해결 과정에서 중요했던 선택

**표기 복구와 추측을 구분했다.** 공백, 하이픈 ID와 슬래시 날짜는 명세가 허용하는 범위에서 표준화하지만, 없는 날짜나 참조 ID를 패턴으로 만들어 넣지 않는다. 파싱 실패를 0으로 바꾸지도 않는다.

**금액은 서로 다른 근거가 일치할 때만 복구한다.** 진료 서비스 상세와 결제를 각각 먼저 집계한 뒤 헤더와 비교한다. 수량·단가·줄 금액 중 하나가 잘못됐더라도, 같은 값을 복사해 맞추는 순환 검증을 피하고 독립 근거가 있는지 확인했다. 카탈로그 단가가 유효한데 상세와 다르면 어느 쪽이 틀렸는지 단정하지 않고 경고를 남긴다.

**국소 검증과 통합 검증을 구분했다.** 한 상세 행이 맞아도 같은 진료의 다른 줄이나 부모 접수가 오류라면 진료 전체는 아직 검증되지 않았다. 노트북의 참조 원본과 다른 노트북의 최종 clean 결과가 자동으로 같아지는 것도 아니므로 통합 단계의 재검증이 필요했다.

원본 총행은 정상·격리·완전 중복 제외로 설명하고 파일·행 위치를 보존한다. 규칙별 오류 건수는 한 행이 여러 규칙에 걸릴 수 있어 단순히 더해 격리 행 수로 사용하지 않는다.

## 4. 분석 질문을 좁히기: 진료과 평균에서 시간대로

초기 일지에는 환자군별 예약·방문 이행 패턴을 검토한 기록이 있다. 최종 개인 분석은 **‘진료과·시간대별 현장접수 불가 패턴을 바탕으로 어느 구간의 정책과 사전 안내를 먼저 점검할 것인가?’**로 좁혔다.

주제 변경은 단순히 다른 차트를 그리는 일이 아니었다. 모집단을 WALK_IN으로 고정하고, 방문 환자가 아니라 **접수 기록 1건**을 단위로 정했다. 접수불가율의 분모는 해당 집단 전체 WALK_IN, 분자는 REJECTED다. LEFT·REJECTED·UNKNOWN을 섞어 자발적 이탈로 설명하지 않는다.

| 분석 기준 | 정의 |
| --- | --- |
| 기간 | 2023.01~2025.12, 36개월 |
| 시간대 | 실제 도착 시각의 1시간 구간. 12시대는 12:00~12:59 |
| 전체 현장접수 | 298,257건 |
| 접수불가 | 73,471건 |
| 전체 접수불가율 | 24.63% |
| 비교 원칙 | 분자·분모 건수를 합산한 뒤 비율 재계산, 미관측은 0과 구분 |

네 구간 합계 **24,996건은 전체 접수불가 기록의 34.02%**다. 높은 비율은 패턴 탐색 기준, 건수는 점검 순서의 근거다. 34.02%를 예방 가능 비율이나 개선 후 회복할 환자 수로 해석하지 않았다.

개인 분석 코드는 CSV 01~03의 월별 합계와 결과 상태 합계를 대조하고, 입력 해시를 기록한다. 보고서는 비율 차이 0·5·10%p와 반복 기준 1/2·2/3·3/4의 9개 조합에서 후보 집합이 유지됐다고 기록한다. 후보 집합의 안정성과 상위 네 구간의 운영 효과 입증은 별개다. 이 글 작성 과정에서 운영 DB를 다시 조회하거나 원천 분석을 재실행한 것은 아니다.

## 7. 활용 제안: 정책 확인 → 안내 대조 → 조건부 개선

분석 결과만으로 ‘안내 부족 때문에 접수가 거절됐다’고 말할 수는 없다. 실제 접수불가 사유와 기존 안내 노출 정보가 없기 때문이다.

1. **정책 확인:** 후보 진료과·시간대의 실제 병원별 접수 조건과 문의 경로를 확인한다.
2. **안내 대조:** 확인한 정책과 방문 전 안내 내용 사이의 누락·불명확한 표현을 찾는다.
3. **조건부 개선:** 보완 필요가 확인될 때 실제 사용하는 안내 채널을 수정한다.
4. **효과 검증:** 변경 시점·안내 노출·접수 사유를 기록하고 적용 전후 및 비교 집단을 설계한다.

이 프로젝트가 제공하는 것은 **어디부터 점검할지에 대한 근거**다. 실시간 접수 가능 여부, 특정 시간 방문 시 진료 보장이나 안내 개선의 실제 성과까지 제공하지 않는다.

## 8. 배운 점과 다음 과제

정제는 데이터 분석의 준비 단계이면서 해석 가능한 모집단을 정의하는 과정이었다. 특히 부모 데이터의 격리와 시간·금액 규칙은 분석할 수 있는 범위를 직접 바꾼다. 내가 만든 표와 팀 전체 DB가 같은 시점·같은 모집단인지 설명하는 문서도 코드만큼 중요했다.

작업 일지에는 진료 시간 관련 값을 확률분포로 보완한 기록도 있다. 이는 관측값 정제가 아닌 **합성 시나리오 수정**에 해당하므로 원본 관측 사실과 분리해야 한다. 해당 생성 코드를 검증하지 않은 상태에서 대기시간 개선을 내 분석의 실측 성과로 사용하지 않았다.

후속 과제는 다음과 같다.

- 분석 CSV·조회 SQL·정제 버전·격리 포함 여부를 같은 manifest로 고정하고 README·DB 추출 합계 차이를 해소한다.
- 실제 운영 자료가 확보된다면 접수불가 사유, 병원 정책, 안내 노출을 추가해 제안의 타당성을 검증한다.
- 미관측 구간과 관측 0%, 기록 건수와 고유 환자 수를 구분하는 기준을 유지한다.
- 생성·복구·검토 정책을 따로 기록하고, 각 단계의 실패·재실행·건수 검증을 연결한다.
