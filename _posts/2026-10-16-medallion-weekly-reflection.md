## 담당 기능 및 구현 내용

팀에서는 기준정보·원천 시스템, 접수, 의사 배치, 수납의 네 관점을 나눴다. 나는 `encounters`, `encounter_services`, `service_catalog` 정제와 공통 코드 점검을 맡고, 이후 현장접수 패턴 분석을 진행했다. 노션과 GitHub의 작업 구조·문서 정리에도 참여했다. 팀 전체의 수납 대사와 의사 배치 시뮬레이션을 내 개인 성과와 섞지 않았다.

담당 산출물은 세 테이블의 정제 노트북, 현장접수 분석용 SQL·Python 코드, 진료과 비교·시간대 히트맵·월별 반복성 차트다. 노트북에서는 정제 CSV와 검토 자료를 저장하고, DB 적재와 통합 검증은 별도 단계로 진행했다.

## 데이터 처리 및 모델 학습 과정

처리 흐름은 원본 보존 → 표준화 → 정상·격리·중복 제외 분리 → DB 적재·통합 검증 → SQL 추출 → 분석·시각화로 구성했다. 별도 예측 모델 학습은 수행하지 않았다. 이번에는 관측된 접수 패턴을 설명하고 정책·안내의 점검 우선순위를 제시하는 것이 목적이었기 때문이다.

수가 버전의 유효기간, 수량×단가와 줄 금액, 서비스 상세합과 진료 총액, 결제·환불 관계를 함께 검토했다. 단순히 결측을 채우는 방식으로는 해결되지 않았다. 다른 테이블도 오염돼 있을 수 있어, 복구의 근거가 서로 독립적이며 일치하는지 확인해야 했다.

## 트러블슈팅 및 해결 과정

### JOIN 이후 금액이 반복되는 문제

SQL 수업의 주문·상세 예제에서는 주문 금액이 상세 행 수만큼 반복됐다. 같은 원리가 프로젝트의 진료·서비스·결제에도 적용됐다. 서비스가 여러 줄이고 결제도 여러 건이면 원본 표를 한꺼번에 붙인 뒤 합산하는 것은 위험하다.

업무 키별로 먼저 합계를 구한 뒤 연결하고, 결합 전후 건수와 금액이 유지되는지 확인하는 과정이 필요했다. SQL을 잘 쓴다는 것은 문법을 아는 것뿐 아니라 **현재 한 행이 무엇을 뜻하는지 끝까지 지키는 것**이라는 점을 다시 확인했다.

정제 결과도 정상·격리·완전 중복 제외로 나누고 사유와 원본 위치를 남겼다. 값이 맞지 않는다는 이유만으로 삭제하거나, 참조 데이터가 불확실한 상태에서 자동 복구하면 나중에 결과를 설명하기 어려워진다. 처리하지 못한 데이터까지 기록하는 것이 재현성과 연결됐다.

### 질문을 좁히고 결론의 범위를 지키기

초기에는 환자군별 예약·방문 이행 패턴을 검토했지만 최종적으로 ‘진료과·시간대별 현장접수 불가 패턴을 바탕으로 사전 안내를 어디부터 점검할까’로 질문을 좁혔다.

전체 현장접수 불가율은 24.63%였고, 진료과 평균 차이는 1.53%p였다. 진료과만 비교하면 차이가 크지 않았지만, 도착 시간대까지 나누면 약 50%의 불가율이 반복되는 구간이 나타났다. 같은 월·진료과 기준과 비교한 반복성과 발생 건수로 네 구간을 점검 대상으로 제시했다.

중요했던 것은 큰 숫자를 찾는 것보다 해석을 멈출 위치였다. 네 구간은 전체 접수불가 기록의 34.02%를 포함하지만, 그만큼 예방할 수 있다는 뜻은 아니다. 접수불가 사유와 안내 노출 자료가 없으므로 안내 부족이 원인이라고도 단정할 수 없다. 합성 데이터의 반복은 생성 규칙의 영향일 수도 있다.

따라서 제안은 ‘안내를 바꾸면 해결된다’가 아니라 **실제 정책을 확인하고, 기존 안내와 대조한 뒤 보완 필요가 있는지 판단하자**는 순서로 정리했다.

## GitHub 및 README 정리

GitHub에서는 테이블별 정제 노트북을 `data/cleaning/`, 주제별 SQL·분석 코드를 `data_analysis/`, 시각화 코드를 `data_visualization/`, 명세·검증·분석 결과와 발표자료를 `report/`로 나누는 구조를 정리했다. 개인 작업을 업로드하는 것에 더해 다른 팀원이 처리 순서와 입력·출력 위치를 이해할 수 있도록 문서화하는 데 참여했다.

README와 발표자료는 **문제 제기 → 데이터와 정제 → 소주제별 분석 → 결과 종합 → 개선 제안과 한계** 흐름으로 구성했다. 내가 맡은 접수 분석이 팀 전체의 기준정보·진료·수납 분석과 어떻게 연결되는지도 함께 정리했다.

### 문서를 정리하며 발견한 보완점

분석·정제·DB 추출 자료의 시점이 다르면 건수도 달라진다. 저장소의 전체 클린 합계와 DB 추출 안내에는 1,000행 차이가 있었고, 현장접수 모집단의 격리 포함 여부 설명도 완전히 일치하지 않았다. 그 차이를 감춘 채 하나의 최종 수치로 쓰기보다 입력·조회 조건·버전을 다시 맞춰야 한다.

작업 일지에는 분포를 사용해 시간값을 보완한 내용도 있다. 합성 시나리오를 만드는 것과 기존 관측값을 정제하는 것은 다른 작업이므로 목적·시드·대상 컬럼·적용 전후를 별도로 기록해야 한다. 생성한 값의 결과를 실측 개선처럼 설명하지 않는 기준이 필요했다.

README와 발표자료는 산출물을 예쁘게 소개하는 작업만은 아니었다. 문제 정의, 데이터와 처리 규칙, 분석 근거, 제안과 한계를 연결하며 서로 다른 문서의 표현과 수치가 일치하는지 확인하는 과정이었다.

## 프로젝트 회고: Keep · Problem · Try

### Keep — 처리 근거와 분석 정의를 함께 기록하기

원본 위치와 변경 이력, 격리 사유를 남기는 방식을 이어가고 싶다. 분석에서도 기간·단위·분모와 미관측 처리 기준을 먼저 정하고, 차트마다 어떤 질문에 답하는지 설명하는 방식을 유지하려 한다.

### Problem — 로컬 정제와 팀 최종 산출물 사이의 간격

내 노트북의 정상 결과가 팀 전체 DB의 최종 정상 결과와 같다고 가정할 수는 없다. 부모 데이터가 격리되면 자식 데이터도 다시 점검해야 한다. 작업 일지의 계획·체크박스와 실제 코드·출력의 완료 상태 역시 함께 관리할 필요가 있다.

### Try — 다음 작업에서 실행할 것

1. **분석 입력 고정:** SQL, 추출 시점, 정제 커밋, 필터와 격리 포함 여부를 manifest로 묶는다.
2. **통합 검증 재현:** 부모·자식 참조와 금액 대사를 같은 실행의 검증 결과로 남기고, 문서 합계 차이를 해소한다.
3. **관측·생성 분리:** 합성 보완 값을 원본과 구분하고 생성 규칙·시드·사용 목적을 기록한다.
4. **제안의 효과 검증 설계:** 정책·안내 변경을 제안할 때 필요한 추가 데이터, 비교 집단과 평가 지표를 함께 적는다.
