## 첫 프로젝트를 돌아보며

이번 주에는 첫 팀 프로젝트인 **Hi스포링**을 돌아보며, 개별 기능을 구현하는 것과 사용자가 이용할 수 있는 서비스를 만드는 일이 어떻게 다른지 정리했다.

Hi스포링은 공공기관 체육복지 담당자가 지역별 이용 현황과 기존 프로그램, 시설 정보를 확인하고, 이를 바탕으로 체육 프로그램을 설계하도록 돕는 플랫폼이다. 지역 현황 조회에서 시설 선택, 프로그램 입력, AI 검토와 운영 계획서 작성까지 하나의 흐름으로 연결하는 것을 목표로 했다.

이전에는 데이터를 분석하거나 모델의 결과를 확인하는 데 관심을 두었다면, 이번에는 그 결과를 사용자가 어떤 화면에서 확인하고 다음 행동으로 이어갈지까지 고민할 수 있었다.

## 담당 기능과 구현 과정

나는 팀장을 맡아 프로그램 설계 기능 개발에 참여했다. 지역 현황 대시보드와 프로그램 설계 흐름을 구성하고, 입력 과정의 예외처리와 AI 분석 결과를 보여주는 UI를 보완하는 작업을 진행했다.

프로그램 설계는 지역 선택, 종목·시설 선택, 운영 정보 입력의 단계로 구성했다. 각 화면을 따로 만드는 것보다 중요한 것은 앞 단계에서 선택한 정보가 다음 단계에 일관되게 전달되도록 하는 일이었다. 지역이나 종목을 바꾸었을 때 기존 시설 선택이 여전히 유효한지, 프로그램 내용을 수정했을 때 이전 AI 검토 결과를 그대로 사용해도 되는지처럼 화면 사이의 관계를 함께 고려해야 했다.

이 과정에서 UI는 보기 좋은 화면만을 의미하지 않는다는 것을 배웠다. 사용자가 현재 어떤 상태에 있고, 무엇을 입력해야 하며, 오류가 발생하면 어떻게 다시 진행할 수 있는지를 알려주는 것도 UI의 역할이었다.

## 데이터 처리와 AI 활용

팀에서는 스포츠강좌이용권 이용현황, 공공체육시설 프로그램, 체육시설 현황 등의 공공데이터를 활용했다. 전국 데이터를 서울 범위로 정제하고, 지역·종목별 집계와 시설·프로그램 조회에 사용할 수 있도록 연결했다.

데이터를 활용하면서 중요하게 본 것은 수치의 의미였다. 이용 실적이 낮다는 이유만으로 수요가 없다고 판단할 수는 없고, 시설 수만으로 공급 부족을 단정할 수도 없다. 관측된 0과 제공되지 않은 값도 구분해야 했다. 분석 결과를 보여주는 서비스일수록 데이터가 설명할 수 있는 범위를 명확히 해야 한다는 점을 확인했다.

이번 프로젝트에서는 별도의 예측 모델을 학습하지 않았다. Gemini API에 지역별 집계와 선택 시설, 프로그램 입력 정보를 전달하고, 이를 바탕으로 지역 현황과 프로그램의 강점·위험요인·개선 방향을 검토하도록 구성했다.

따라서 핵심은 모델 학습 성능보다 **어떤 근거를 전달하고, 어떤 형식으로 응답받으며, 그 결과를 어떻게 검증하고 사용할 것인가**에 있었다. AI 결과도 최종 판단을 대신하는 답이 아니라 담당자의 기획을 보완하는 자료로 다루었다.

## 기술 스택을 선택하고 연결하며 배운 점

서비스는 Django를 중심으로 HTML·CSS·JavaScript, HTMX, ECharts 등을 연결하는 구조로 구성했다. Python 기반의 데이터 처리와 웹 요청 처리를 같은 프로젝트에서 다루고, 화면 일부만 갱신하거나 지역별 분포를 시각화하는 역할을 각각 나누었다.

데이터 저장은 CSV와 메모리 캐시를 사용했다. 선정한 데이터 대부분을 파일로 제공받고, 서비스 범위를 서울로 한정한 상황에서 데이터를 정제해 활용하기 위한 선택이었다. 다만 전국 단위로 확장하거나 복잡한 조회와 지속적인 갱신이 필요해지면 DB와 색인 구조를 검토해야 한다는 한계도 남았다.

여러 기술을 사용했다는 사실보다, 각 기술이 어느 문제를 해결하는지 이해하는 것이 중요했다. 프레임워크와 라이브러리를 연결해 기능이 동작하더라도, 데이터와 요청이 이동하는 흐름을 이해하지 못하면 오류가 발생했을 때 원인을 찾기 어려웠다.

## 예외처리와 트러블슈팅

프로그램 설계 과정에서는 정상적인 입력뿐 아니라 사용자가 선택을 바꾸거나 데이터를 찾지 못하는 상황도 고려해야 했다.

예를 들어 시설 검색 결과가 없더라도 실제로 후보 시설이 없는 것인지, 검색어 때문에 보이지 않는 것인지는 다르다. 또한 AI 검토 이후 프로그램 정보를 수정했다면 기존 검토 결과는 현재 입력과 맞지 않을 수 있다. 서비스에서는 이러한 상태를 구분하고, 재검토하거나 이전 결과의 포함을 해제하도록 처리했다.

팀 차원에서는 배포 환경의 초기 데이터 적재 문제도 다뤘다. Gunicorn의 프로세스 생성 시점과 CSV 적재·스케줄러 시작 시점이 맞물리는 문제에 대해 워커 초기화 이후 실행하도록 구조를 분리한 기록이 있다. 이를 통해 로컬에서 동작하는 코드라도 배포 환경에서는 실행 순서와 프로세스 구조를 다시 확인해야 한다는 점을 배웠다.

모든 오류를 자동으로 해결하는 것보다, 실패한 구간을 알리고 가능한 기능을 유지하는 것도 중요했다. AI 검토가 실패하더라도 기본 계획서를 작성할 수 있도록 한 구조가 그 예다.

## GitHub와 README 정리

프로젝트를 설명하려면 코드뿐 아니라 왜 만들었고, 누가 무엇을 맡았으며, 어떤 데이터와 처리 흐름을 사용하는지도 함께 정리해야 했다.

저장소의 README에는 팀별 역할, 프로젝트 배경, 기술 스택과 구조, 요구사항, 데이터 처리, 예외처리와 구현 화면을 담았다. 현재 구현된 기능과 향후 개선사항을 나누어 기록하는 것도 중요했다.

특히 데이터 배치를 실행하는 것과 외부 최신 원본을 자동으로 수집하는 것은 다르다. AI 호출이 동작하는 것과 실제 기관에서 효과가 검증된 것 역시 구분해야 한다. 문서화는 결과물을 소개하는 작업이면서, 구현 범위와 한계를 다시 점검하는 과정이기도 했다.

## 이번 프로젝트에서 얻은 것과 다음 목표

좋은 팀원들과 함께 기획부터 UI 구성과 수정, 기능 연결까지 경험할 수 있어 뜻깊었다. 각자 맡은 코드가 하나의 서비스로 연결되는 과정을 보면서, 내 기능의 완성도만큼 다른 기능과 만나는 지점을 이해하는 일이 중요하다는 것을 느꼈다.

AI를 활용한 바이브 코딩은 익숙하지 않은 기술에 접근하고 아이디어를 빠르게 구현하는 데 도움이 됐다. 동시에 원하는 결과를 얻으려면 요구사항을 구체적으로 설명하고, 생성된 코드의 동작과 예외 상황을 직접 검토해야 했다. 구현 속도가 빨라져도 무엇을 만들지 판단하고 결과를 확인하는 책임은 남아 있었다.

다음 프로젝트에서는 구현을 시작하기 전에 데이터 구조와 기능 간 입력·출력, 예외 상황을 더 명확히 정리하고 싶다. 테스트 결과도 확인한 범위와 함께 기록해, 기능을 추가하거나 수정한 뒤에도 기존 흐름이 유지되는지 점검하려 한다.

이번 경험을 바탕으로 데이터를 분석하는 데서 더 나아가, 분석 결과가 사용자의 판단과 행동에 도움이 되는 서비스로 이어지도록 고민하고 싶다.
